# F01-F06 foundation handoff

Scope is PDF pages 1-17, ending after F06. C01 begins on page 18 and is deferred. The original prompt pack is preserved under `output/pdf/`. This change establishes contracts and locations for future features; it does not install any of the twelve real puzzles, collect or play tapes, accelerate hazards, author restoration assets or play beauty shots.

## Changed behavior and ownership

- F01: `FOUNDATION_AUDIT.md` records engine/code/assets, zone mappings and observations from all ten references. `EXECUTION_LEDGER.md` tracks assignments and decisions.
- F02-F04: `scripts/tasks/repair_catalog.gd`, `repair_runtime.gd` and `repair_actions.gd` define additive stable records, host validation, transient operator leases and future puzzle-validator registration. `ColonyState.repair` serializes the new records and existing snapshot replication carries them to clients. Session replica records carry live leases; disk saves do not.
- F03: crew switching retains existing exclusive ownership and hub requirements; explicit release also requires a safe hub. Unsafe atmosphere/health/exposure guards prevent swapping out of an encounter. A hazardous disconnect uses existing recovery before parking; safe suited disconnect retains its old parking behavior. Teleports recalculate the outside flag immediately. The required specialty remains identical in solo and LAN. Wrong-role answers identify the needed specialty.
- F05: `TaskPanel` extends the current native `UiPanel`, including pending/rejected host results, progress, reset/cancel/success, labeled controls and safe interruption. `TaskSamplePanel` is a UI-only demonstration, accessed by `UiRoot.open_task_sample()`. It changes no colony records or rewards. Urgent existing system alerts are readable above panels and close a task safely.
- LAN integration: `GameMain` only reloads its current scene after host loss when it owns that scene. Embedded game instances used by LAN tests/tools retain their parent scene instead of attempting to reload a null/unrelated current scene.
- F06: `data/stations_repairs.json` provides 19 measured locations (12 tasks, six future tape pickups, one future player). `StationCatalog` retains their stable metadata. `WorldCollision` adds compact original non-solid markers. Reserved station panels clearly identify deferred functionality. New-game crew positions and recovery spots use collision-probed Med Bay offsets; normal load retains the saved controlled character's position. Older saves gain missing new stations and corrected safe recovery spots additively. A saved remote astronaut in danger retains its saved encounter position/exposure until controlled, rather than receiving a free rescue through reload.

## Public API and stable records

- Room IDs: `command_center`, `power_supply`, `greenhouse`, `green_dome`, `med_bay`, `hangar`. Hangar supports actual zones `Hangar bay` and `Airlock`.
- Task IDs: `T01`..`T12`; repair anchor IDs: `repair_t01`..`repair_t12`. Exact roles, rooms and titles are canonical in `RepairCatalog.TASKS`; actual positions are canonical in `data/stations_repairs.json`.
- Cassette IDs reserved by the station data and accepted by state restoration: `cassette_<room_id>`. Collection remains unimplemented. The sole future playback anchor is `cassette_player_command_center`.
- `ColonyState.repair` version 1 contains `rooms`, `tasks`, `collected_cassettes` and `seen_beauty_shots`. Existing saves missing the record migrate in memory to deterministic defaults derived from their existing colony seed. The established save envelope and LAN protocol remain compatible because their existing dictionary schema already transports additive keys.
- Task records include `room_id`, `required_specialty`, `anchor_id`, `puzzle_seed`, `fault_generation`, `progress`, `condition`, `first_completed`, `puzzle_state` and `resume_supported`. Room first completion, current condition/wear and seen-shot history are separate. A later maintenance fault cannot erase the first milestone.
- Actions `task_claim`, `task_resume`, `task_release` target the task anchor and require `generation: int`. `task_move` also requires `move: String` and `value: int`. Action ownership, reach, role, room, generation and lease are revalidated on the host. Client completion flags are rejected by the parameter schema.
- One lease per task expires after 30 active real seconds without accepted activity. Distinct tasks accept separate operators. Disconnect, death/recovery, switch, reach/role loss and host fault regeneration release the lease. Genuine global pause freezes lease time. Restart discards leases.
- Stopping host LAN also releases all remote crew ownership and leases before closing the transport, allowing the host to continue the colony offline without ghost operators.
- Future task implementations call `session.repair_runtime.register_rule(task_id, validator, supports_resume := false)` on the host. The pure validator receives a copied task and `{move, value}`, and returns `{accepted, puzzle_state, progress, complete}`. Its completion decision is authoritative; it may authorize a reset of partial progress. Disk projection preserves partial puzzle state only when the rule explicitly supports safe resume. LAN snapshots retain current live puzzle state. With no registered rule, all puzzle moves fail closed. Synthetic tests use their own rule; no production room puzzle is registered.
- Future wear code calls host-only `begin_fault(state, task_id, puzzle_seed, condition)` to advance generation and reset the current puzzle while preserving narrative achievements. No client action exposes this API.
- `TaskPanel.configure_task(...)` configures headings and identity; concrete puzzles fill `play_area`. `move_requested` and `reset_requested` allow custom input adapters; `request_host` uses `GameServices.request`. `apply_host_state`/`accept_host_result` update the presentation. Concrete future widgets own refreshing their puzzle-specific controls from authoritative records and resuming an expired claim.
- `CharacterState.lethal_exposure_seconds` is an inert durable real-second accumulator for S01. It is saved, restored and replicated, and a positive value blocks crew switching. The existing recovery path clears it. This foundation never advances it or changes existing survival damage. S01 must use this field for elapsed exposure rather than a transient UI timer; reload therefore cannot reset a future ongoing encounter. No offline deterioration or exposure time is added.
